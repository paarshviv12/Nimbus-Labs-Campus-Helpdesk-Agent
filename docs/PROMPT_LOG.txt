F.2 Reflection (300 words)
Skills, plugins, MCP and worktrees answer four different questions. A Skill
answers “how should the agent behave on this kind of task?” It is instructions
plus small files, loaded when relevant. A plugin answers “how do I ship and

                Paarshvi Vijoy | Roll no: 150096725188 | Cohort: Jeff Bezos | Page 12
install that behaviour as one unit?” It bundles skills, commands, hooks and MCP
entries. MCP answers “how does the agent reach live data or actions?” It is a
protocol between a client and a server. Worktrees solve a different problem from
the other three: “how can several coding sessions work on one repository without
trampling each other?” That is a Git feature for developers. It does not change
what the agent knows or can do.
I would choose a Skill over an MCP tool when the need is guidance and the data
is small and static. My timetable skill needed only a CSV and a rule, quote the
row or say not found, so a skill with a script was enough. An MCP tool earns its
place when the data is live, access-controlled or changes often, such as real fee
status, because the server can validate input and enforce permissions in code
instead of hoping the model follows text.
I would never delegate these without review: merge-conflict resolution,
installing or updating third-party plugins, hooks or MCP servers (they run with
my permissions), security checks, and every citation or command I submit. This
assignment showed why. The first-pass answers invented a package, a git
subcommand, a revision date and a paper, and every one looked fluent. The fix
was always the same: open the official page, run the command, or write
Unverified. Even my verified work has limits. I did not test the hook or the
server inside a live Claude session, so I say so instead of implying it.
